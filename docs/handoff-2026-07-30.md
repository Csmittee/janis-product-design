## What's built and locked

**Rib profile** (`t1`..`t7u`, `T4U`, `t6be` — full labeled diagram:
`docs/rib-cb1-terminology.png`): t1 (handle bore) → t2/t3 (up the A-B
wall) → t4 (B-C/C-D miter) → T4U (perpendicular from apex C, the real
top-line anchor) → t5 → t6be/t7/t7u (CB1 bracket neck) → t6 (pivot
bore). This profile itself is locked — the only things that move are
CB1's own position/size, the shared pivot, the handle, and now the tray
hinge Z.

**CB1 is 2 real, separate parts**:
1. **The bracket** (`cb1_link_2d()` → `Ua`/`Ub`/`Uc`, one single
   polygon) — locked, wraps half of a 4" square tube on all 3 ribs.
2. **The counterweight pipe** (`cb1_pipe()`) — a real 4" square tube,
   both ends capped, real computed mass **~8.0kg** (matches Janis's own
   recollection and the old locked spec from `archive/BBQ-offset-
   smoker-base-v9.scad` almost exactly). This had been missing (never
   re-added as a mass) since v11 — restored this session. Its
   cross-section is built with the SAME `tangential_pt()`/
   `freeze_from_open()` frame the bracket uses, so it stays flush and
   aligned with the bracket's own slot (fixed a real angle bug this
   session — first pass had it axis-aligned instead of DE-tangent).

**4 parametric knobs** a future round can move without touching
anything else: CB1 position/size (`CB1_EDGE_FRAC`/`CB1_STANDOFF`/
`CB1_OD`), the shared pivot (`FC_Y`/`FC_Z` in `BBQ-chambers-v26.scad`),
the handle (`HANDLE_Y`/`HANDLE_Z`), and the tray hinge Z (`HINGE_Z`,
itself derived from the handle boss so it self-adjusts if the handle
ever moves).

**Prep trays** — relocated this session (`docs/tray-relocation-
bracket.md` has the full derivation + diagram) to clear the grab
handle, which they used to collide with:
- New triangular gusset bracket (`tray_bracket()`, 4 copies, apex A /
  hal / al) mounted on face HA (the existing chamfer wall below apex
  A — confirmed by Janis: the octagon's 8th vertex, going around the
  alphabet, is "H"; face HA is the face just before apex A). `hal`
  pinned to apex H exactly (not a plain 200mm drop past it, which
  floated in open air — a real fix caught early on).
- New `HINGE_Z` = lowest point of the handle boss minus 15mm.
- `TRAY_MOUNT_GAP`=16mm (real fix, Janis's own catch): the tray plate
  used to still mount flush with the pivot line, overlapping the
  hinge block's own widened footprint, so there was never a real gap
  behind the tray for a folded link to hide in. Plate (and skirt) now
  start flush with the hinge block's own outer tip.
- A folding support link (`tray_link()`), now real hardware-style
  geometry, not just a length: a **flat 15mm-wide steel strip** (was a
  round rod), with a genuine ~10mm **lap overlap** at the middle pivot
  (each link's real length is `(span+overlap)/2`, not half the span),
  a **U-shaped clevis + pin at both `ts` and `tt`**, and `tt` pulled
  15mm clear of the tray's own underside so it no longer visibly
  penetrates the tray surface.
- **v16: the link became genuinely angle-dependent** (Janis's own direct
  catch: "you got to wire it"). `tt` rotates rigidly with the tray;
  `ts` was made a slider (a real workaround, at the time, for what
  turned out to be a fold-DIRECTION bug — see v17 below).
- **v17: fold direction fixed, LOCKED, never to change again.** Janis's
  own direct catch: v16's `angle_deg` convention (-90=stowed) actually
  swung the tray tip UP past apex A, not down toward the ground —
  confirmed via a real colored render. Locked spec:
  **`tray0_angle_deg`/`tray1_angle_deg`: 0=deployed (horizontal) ..
  +90=stowed (vertical, tip toward the ground)**, rotating clockwise
  about X (viewed from +X) as it deploys. The tray's own hinge is the
  fixed center of rotation, unchanged.
- **v17: link kinematics rebuilt to match**, via a real taught 2-bar-
  link exercise (a triangle a/b/c, checked against a labeled simulation
  before applying it) — see `docs/tray-relocation-bracket.md`'s "v17"
  section for the full derivation. Key result: under the CORRECTED fold
  direction, the fixed-`ts`-to-rotating-`tt` distance genuinely
  *shrinks* as the tray folds (matching the triangle's own "chord
  shrinks as the arms close" behavior) — so `ts` reverts to Janis's
  ORIGINAL spec, **a true fixed anchor at `al`, no slider needed**. The
  give is now in the link's own middle lap-joint (`lc`), solved via a
  real circle/circle intersection, picking the root closer to apex A
  (matches Janis's own description of how the joint should move). The 2
  link halves are also now **split in depth** (not coplanar) — same
  fix real hinges/scissors use, checked via a real rectangle-overlap
  simulation first — combined stack held to a real **10mm total**
  (`TRAY_LINK_STACK_T`), not additive, per Janis's own correction (the
  2 halves nest/wrap into each other, not stack side by side).
  Re-verified via an isolated collision probe: **empty (no collision)
  from 0° to about 86°** — the entire normal operating range, a large
  improvement over v16. **Disclosed, not fully resolved** (Janis's own
  call — this link isn't critical): a real, small collision remains
  from about 87° to 90°, where `ts`/`tt` nearly coincide, making the
  circle intersection ill-conditioned — inherent to this near-degenerate
  geometry, not fixable by a different root choice. Accepted as a
  practical ~86° fold limit.
- **v18: pivot relocated + link sizing fixed, closes the v17 gap
  completely.** Janis's own direct teaching after the v17 render: "it
  seem like you put in on the apex a and al plane not the tip of the
  small hinge notch" — v17's pivot was still at the OLD inner point
  (`Y=-HINGE_PIVOT_OFFSET`), not the hinge block's own real outer tip.
  Fixed: pivot now at `Y=-HINGE_OUT` (matches a real door hinge's own
  knuckle position, at the leaf's outer edge). `TRAY_LINK_C_HALF` also
  fixed to exactly half the deployed reach (no lap-overlap padding) —
  proven via the law of cosines to give exactly 180° at 0° and stay
  smooth (not ill-conditioned) across the whole sweep; the real slop a
  lap joint needs is what Janis's own **slotted pivot** correction
  provides instead of a fixed pad. Also caught and fixed a real
  non-manifold regression along the way: mounting the plate exactly
  coincident with the hinge block's own face made the full assembly
  `Simple: no` at intermediate angles (only caught via a real
  full-assembly sweep, not the isolated probe) — fixed with the
  project's own `e` epsilon (genuine tiny overlap, not a coincident
  face). Re-verified: **empty (no collision) across the ENTIRE 0-90°
  range** — the v17 87-90° gap is fully closed. Still not perfect
  (Janis's own call): the fold angle at the middle joint reaches ~11°
  at full stow, not a literal 0° — the real slotted pivot (not modeled
  precisely) would take up this last bit.
- **v19: two real defects found by Janis from direct inspection of the
  v18 render, both fixed.** (1) `ts`'s own hinge was genuinely SINKING
  INTO `tray_bracket()`'s own solid wedge — `al` (where `ts` lives) is
  literally one of the bracket's own 3 triangle vertices, so
  `hinge_u(ts,...)`, centered exactly on that vertex, overlapped the
  bracket's own material (confirmed via a real `intersection()` probe:
  22 vertices, 3 volumes — a genuine overlap, never caught before since
  prior collision probes only checked the link against the tray PLATE,
  never against `tray_bracket()` itself — a real QA gap now closed).
  (2) `lc` (the middle lap-joint) was landing 80-110mm away from both
  `ts` and `tt` at full fold instead of visibly aligning with them, per
  Janis's own explicit alignment requirement ("hinge must overlap each
  other"). Root cause proven via a free-body diagram: with `ts`-to-`tt`
  shrunk to ~22mm at 90° but each rigid link half fixed at ~110.8mm, a
  rigid circle/circle solve has no choice but to bow `lc` far out — and
  forcing `lc`'s Y into the desired band leaves the other half ~21mm
  SHORT of its own fixed length, physically impossible for a rigid bar.
  Janis's own resolution: "we do not change the link length, we allow
  the pivot pin to slide along the link to compensate the diff of
  length need at each require angle" — a telescoping-slot mid-joint,
  not a fixed-length rigid 2-bar link. `lc` is now simply the MIDPOINT
  of `ts` and `tt` at every angle, which keeps `ts`-`lc`-`tt` exactly
  collinear (a straight, shortening strut, not a bowing 2-bar link) and
  puts `lc`'s Y automatically between `ts`/`tt`'s own Y at every angle
  by construction — which, as a direct consequence, also keeps `lc`
  clear of the bracket. The v18-era internal depth-split
  (`TRAY_LINK_X_SPLIT`, for 2 bowing coplanar bars) is retired (no
  longer bows); instead the WHOLE link is offset clear of the
  bracket's real X-span via a new `TRAY_LINK_BRACKET_CLEAR`. Re-verified
  across the entire 0-90° sweep: full-assembly `Simple: yes`, link vs.
  bracket empty, link vs. tray plate empty, link vs.
  `front_wheel_support()` empty, and the link's own self-manifold-ness
  clean (no self-intersection at the now-collinear `lc`). Disclosed:
  the real slot magnitude this now needs is large (~100mm of working
  travel per side, each half's own fixed length unchanged) — schematic,
  not modeled as a literal slot mechanism. See
  `docs/tray-relocation-bracket.md`'s "v19" section.
- A 10mm skirt (`TRAY_SKIRT_H`) on the tray's **tip and both left/right
  side edges** (moved off the hinge-side edge — the first pass visibly
  sank into the hinge block, a real defect Janis caught by eye since
  it's not a manifold error, just overlapping solid material).

## Moment analysis result (`docs/lid-hinge-moment-analysis.md`)

Real gravity moment 0-90°, computed from actual STL-derived mass/CG
data (not hand math). With the CB1 pipe restored:

| Janis's requirement | Target | Computed | Verdict |
|---|---|---|---|
| Startup lift at 0° | 3-7 kgf | 2.5 kgf | close, slightly under |
| Zero moment at/after 45° | crosses negative ≥45° | crosses at 89.2° | technically meets "or later," but very late |
| Gentle negative before 90° | negative before 90° | negative only in the last ~1° | marginal |
| Self-holding at 90° | ~5 kgf pull needed to close | -0.02 kgf (near-neutral) | fails |

**Open decision, not yet resolved**: the pipe's current position/size
(tuned for bracket clearance) lands the door almost exactly *balanced*
at full open rather than *self-holding*. Hitting the full target needs
more counterweight leverage — a heavier pipe, a longer `CB1_STANDOFF`,
or a different `CB1_EDGE_FRAC`. Not changed this session since Janis
called the bracket "locked" — this needs an explicit decision before
anyone moves CB1's position/size.
